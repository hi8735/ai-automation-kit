# 자동화 문서 틀 — `automations/<이름>/AUTOMATION.md`

사용자의 첫 자동화는 이 틀로 만든다. 핵심은 **인터뷰에서 들은 그 사람의 업무 방식**을 빠짐없이 옮기는 것이다. 일반론("보고서를 깔끔하게 작성한다")은 쓸모없다. 구체적인 규칙("거래처별로 묶고, 지난주보다 20% 이상 줄어든 곳은 굵게")이 자동화를 쓸모 있게 만든다.

이 문서는 사용자도 직접 열어 읽는다. 쉬운 말로 쓴다.

## 틀

```markdown
# 주간 발주 집계 보고서 (weekly-report)

실행: 이 폴더에서 Claude Code 를 열고 `/run weekly-report`

## 무엇을 하나
(이 업무가 무엇이고, 결과물이 누구에게 어떤 용도로 가는지 2~3줄)

## 입력
- 위치: `inputs/` 폴더 — 실행할 때 **먼저 이 폴더에서 새로 넣은 파일을 찾아** 그걸로 할지 묻는다. 없을 때만 붙여넣기를 요청한다.
- 어떤 파일: (예: 이번 주 발주 내역 엑셀. 시트 이름, 주요 열 이름)
- 입력이 없거나 형식이 다르면: 사용자에게 무엇이 필요한지 알려주고 멈춘다.

## 처리 단계
1. (인터뷰의 실제 단계를 그대로, 구체적으로)
2.
3.
(Python 프로그램을 쓰면: 어느 단계에서 `automations/weekly-report/script.py` 를 어떻게 실행하는지)

## 규칙
- (정해진 규칙들 — 정렬 기준, 묶는 기준, 계산 방법, 표기 방식)

## 판단이 필요한 부분 (자동화가 정하지 않는다)
- (예: 지연 사유 해석 → "확인 필요" 로 표시하고 사용자에게 묻는다)

## 예외
- (가끔 생기는 경우와 처리 방법)

## 결과
- 형식: (예: 아래 양식의 표 + 요약 3줄)
- 저장: `outputs/weekly-report-YYYYMMDD-HHMM.md` (또는 .xlsx / .csv). **이전 결과를 덮어쓰지 않는다.**
- 끝나면 사용자에게: 결과 파일 위치 + "확인 필요" 항목 목록

## 결과 양식
(가능하면 사용자가 평소 쓰던 결과물의 구조를 그대로 옮긴다. **예시 값은 가짜로** 쓴다 — 실제 손님·거래처 이름, 전화번호, 금액을 이 문서에 남기지 않는다.)
```

## 체크

만들고 나서 스스로 확인한다:
- 이 문서만 읽은 다른 사람이 같은 결과를 낼 수 있을 만큼 구체적인가?
- 인터뷰에서 사용자가 말한 판단 기준과 예외가 다 들어갔나?
- 사람이 판단해야 할 것을 자동화가 마음대로 정하고 있지 않나?
- 입력 파일이 없거나 다를 때 어떻게 할지 적혀 있나?
- 같은 입력을 두 번 넣었을 때 결과가 망가지지 않나? (중복 반영 등)
