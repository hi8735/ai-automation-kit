# /build — 첫 자동화 만들기

목표: 사용자가 내일부터 **혼자서 다시 쓸 수 있는** 자동화를 만든다. 대단한 것보다 **확실히 돌아가는 작은 것**이 낫다. 다음 날 깨질 것을 "완성" 이라고 하지 않는다.

## 0. 준비 확인

1. `results/interview.md` 를 읽는다. 선택한 업무, 실제 단계, 완성된 모습, 샘플 파일이 있어야 한다.
   - 기록이 없으면: "어떤 일을 자동화할지 먼저 정해야 해요. `/start` 로 시작해볼까요?" 하고 멈춘다.
   - 등급이 A 가 아니면: 왜 오늘 만들기 어려운지 다시 짧게 말하고, 그래도 일부라도 해볼지 묻는다.
   - 샘플이 없으면: 샘플 준비 방법을 안내한다 (`inputs/` 에 넣기, 민감한 부분은 지우거나 가짜 값으로).
2. `stage` 를 `build` 로 갱신.

## 1. 방식 고르기

**기본은 "자동화 문서" 다.** 업무 절차를 `automations/<이름>/AUTOMATION.md` 에 구체적으로 적어두고, 사용자가 `/run <이름>` 을 치면 Claude 가 그 문서대로 처리한다. 인터뷰에서 정리한 업무 절차가 그대로 문서 내용이 된다. 사용자가 탐색기·Finder 에서 이 문서를 직접 열어보고 고칠 수도 있다.

| 상황 | 방식 |
|---|---|
| 문서·글·요약·분류·정리, 양이 많지 않음 (대부분) | **자동화 문서**만 |
| 엑셀(.xlsx)을 읽거나 만들어야 함 | 자동화 문서 + 같은 폴더의 작은 Python 프로그램 (`guide/python-setup.md`) |
| 수백~수천 건을 똑같이 처리, 매번 결과가 완전히 같아야 함 | 자동화 문서 + Python 프로그램 |

- Python 이 필요한데 없으면 `guide/python-setup.md` 의 절차를 따른다. **반드시 본인 동의를 먼저 받는다.** 설치가 막히면 우회하지 말고 CSV 방식으로 낮추거나, 기록에 "환경 제약" 으로 남긴다.
- 방식을 한두 문장으로 설명하고 진행해도 될지 묻는다:
  > "이렇게 만들어볼게요. 앞으로 `inputs` 폴더에 이번 주 파일을 넣고 `/run weekly-report` 라고 치시면, 제가 정해진 형식으로 보고서 초안을 만들어 `outputs` 폴더에 저장해 드려요. 괜찮으세요?"

## 2. 만들기

`references/automation-template.md` 를 읽고 그 틀로 만든다.

- 위치: `automations/<이름>/AUTOMATION.md` (폴더가 없으면 만든다).
  - **이름은 영어 소문자·숫자·하이픈만** 쓴다 (예: `weekly-report`, `deposit-check`). 한글 이름은 윈도우에서 깨질 수 있다. 2~3개 제안하고 번호로 고르게 한다.
- 결과물은 `outputs/` 에 저장한다 (없으면 만든다).
- **안전 규칙 (예외 없음)**
  - `inputs/` 의 원본 파일과 사용자의 다른 파일은 **고치거나 지우지 않는다.** 원본을 업데이트하는 업무(예: 미수금 장부에 입금 반영)라도 결과는 `outputs/` 에 **새 파일**로 만들고, 원본에 옮기는 건 사용자가 직접 한다.
  - 메일·문자·카톡 보내기, 업로드, 결제, 사이트 입력처럼 **밖으로 나가는 동작은 자동화가 하지 않는다.** 보낼 내용은 초안 파일로만 만든다.
  - 이 두 규칙을 `AUTOMATION.md` 의 "하지 않는 것" 에 적어 둔다.
- Python 프로그램이 필요하면 같은 폴더에 둔다 (`automations/<이름>/script.py`). 짧고 읽기 쉽게, 한글 처리(UTF-8, CSV 는 `utf-8-sig`/`cp949` 둘 다)를 처음부터 고려한다.
- 프로그램 실행 명령은 **이 PC 에서 실제로 동작한 명령**(`py`, `python`, `python3`, 또는 python.exe 전체 경로 중)으로 `AUTOMATION.md` 와 `HOW-TO-USE.md` 에 적는다. 추측한 명령을 적지 않는다.
- **`.claude/` 폴더 안에는 만들지 않는다.** (Claude Code 가 보호하는 폴더라 확인 창이 뜨거나 막힌다)
- 인터뷰에서 들은 **판단 기준, 예외 처리, 결과 형식**을 구체적으로 적는다. 이게 자동화 품질의 전부다.
- 사용자에게 묻지 않은 규칙을 몰래 넣지 않는다. 필요해 보이는 규칙(예: 파일이 여러 개면 어느 걸 쓸지)은 사용자에게 물어서 정한다.
- **사용자가 매주 파일 이름을 바꾸거나 손질하게 만들지 않는다.** 만들기 전에 "실제로 내려받으면 파일 이름이 어떻게 나와요?" 를 묻고, 파일은 이름이 아니라 **내용(열 이름, 첫 줄 등)으로 구분**한다. 기간·날짜도 가능하면 파일 내용에서 읽는다. 목표는 "받은 파일을 그대로 `inputs` 에 넣으면 끝" 이다.
- 사람이 판단해야 하는 부분은 자동화가 대신 정하지 않게 한다 — "확인 필요" 로 표시하고 사용자에게 묻게 만든다.
- 파일 만들기가 실패하면: 정해진 위치 말고 다른 구조를 새로 지어내지 않는다. 무엇이 막혔는지 쉬운 말로 설명하고, 확인 창에서 '예' 를 눌러야 하는 상황인지 확인한 뒤 다시 시도한다. 그래도 안 되면 기록의 "막힌 점" 에 남긴다.

## 3. 시험하기 (반드시)

1. 사용자에게 "이제 실제로 돌려볼게요" 라고 알리고, **방금 만든 `AUTOMATION.md` 의 지침 그대로** (`/run` 과 같은 방식으로) `inputs/` 의 샘플로 실행한다.
2. 결과를 보여주고 묻는다: "평소에 직접 만드시던 거랑 비교해서 어때요? 틀리거나 다른 부분이 있어요?"
3. 고칠 점을 문서·프로그램에 반영하고 다시 돌린다. 2~3 번 반복해도 좋다.
   - 다시 돌릴 때 이전 결과를 **덮어쓰지 않는다** (결과 파일 이름에 날짜·시각이 붙게 만든다).
   - 예외 상황을 시험하려고 가짜 파일을 만들었으면 `automations/<이름>/test-files/` 에만 두고, `HOW-TO-USE.md` 에 "시험용 가짜 파일이에요, 지워도 돼요" 한 줄을 적는다. `inputs/` 에 시험 파일을 남기지 않는다 (다음 실행에 섞인다). 사용자의 연습용 샘플이 `inputs/` 에 남아 있으면, 실제로 쓰기 전에 옮기거나 지워야 한다고 알려준다.
4. 사용자가 "이 정도면 쓸 만하다" 고 하면 완성. 끝까지 안 되면 어디까지 됐는지 정직하게 정리한다 (`일부`).

## 4. 사용법 남기기

- 같은 폴더에 `HOW-TO-USE.md` 를 짧게 만든다: 무엇을 어디에 넣고, 무엇을 치고, 결과가 어디에 생기는지, 주의할 점. **`/run` 사용법만 적는다** — 터미널·명령어로 직접 실행하는 방법은 쓰지 않는다.
- 사용자에게도 3줄 이내로 알려준다. 예:
  > 1. `inputs` 폴더에 이번 주 파일을 넣고
  > 2. 코치 화면(또는 이 폴더에서 연 Claude Code)에 `/run weekly-report` 라고 치시면
  > 3. `outputs` 폴더에 결과가 생겨요.
- 실제로 동작하는 방법만 안내한다. 시험하지 않은 사용법을 알려주지 않는다.

## 5. 기록하고 마무리

- `results/interview.md` 의 "만든 자동화" 를 채운다 (결과: 성공 / 일부, 사용법, 남은 문제).
- "이제 `/report` 로 진행자분께 보낼 리포트를 만들 수 있어요. 해볼까요?" 로 넘긴다.
